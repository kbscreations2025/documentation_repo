Centralized Login & Access Management

Everything your app's backend needs to authenticate against the central auth service — the full /api/v1 contract, the OTP-per-device flow, and the two behaviors that trip people up: the concurrent-login limit and the refresh pattern.

Authenticating requests

Every call to /api/v1/* is made server-to-server from your app's own backend — never from the browser — and carries these two headers.

X-Client-Id: cid_your_client_id
X-Client-Secret: <ask your superadmin for this>

Your app is registered as an application in the central dashboard (Superadmin → Applications), which is what generates this client_id/client_secret pair. Pick your app above to fill its real client_id into every example on this page — ask your superadmin for the matching secret over a private channel, it's never shown in this guide or in Swagger.

Every response shares one envelope shape: { status: "success" | "otp_required" | "session_limit_reached" | "error", ... }, identical across every endpoint below.

Login flow overview

Design your login screen as a two-step form. This is the path a brand-new device takes end to end.

1
User submits email + password to your backend, which calls verify-login.
2
A device that hasn't proven itself gets back otp_required — never tokens directly.
3
The superadmin reveals a fresh 6-digit code from the dashboard and shares it with the user out-of-band.
4
User enters the code, your backend calls verify-otp — this returns tokens and a new device_token.
5
Store all three: access_token, refresh_token, device_token. Send device_token back on this device's future verify-login calls to skip the OTP step entirely.

/verify-login

Validates credentials. Behavior branches on whether this device has a valid device_token from a prior verify-otp.

POST/api/v1/verify-login
Request
{
  "email": "user@example.com",
  "password": "their-password",
  "device_token": "<optional — omit on a new device>",
  "force_logout_others": false,
  "logout_session_ids": []
}
New device → OTP required
{
  "status": "otp_required",
  "message": "an OTP is required to complete this login…",
  "otp_expires_at": "2026-08-27T07:28:23Z"
}
Trusted device → tokens directly
{
  "status": "success",
  "user": { "user_id": "…", "name": "Jane Doe", "role": "Team Mate", "permissions": ["invoice:read"] },
  "access_token": "eyJhbGciOi…",
  "refresh_token": "eyJhbGciOi…",
  "permissioned_applications": [],
  "device_token": null
}

Either path can instead return session_limit_reached — see below. Resend with force_logout_others: true (kill every blocking session) or logout_session_ids: [...] (kill only the ones picked, for a limit above 1) to proceed.

/verify-otp

Completes the login started above. The OTP is generated by verify-login and shared by the superadmin — this API never emails or texts it to the end user directly.

POST/api/v1/verify-otp
Request
{
  "email": "user@example.com",
  "otp": "926563",
  "force_logout_others": false,
  "logout_session_ids": []
}
Success
{
  "status": "success",
  "user": { … },
  "access_token": "eyJhbGciOi…",
  "refresh_token": "eyJhbGciOi…",
  "device_token": "x2Y5wvY4WqDLHwEPu_vSOOs8DctUM8DMkP8mbkBaVlM"
}

The code is consumed the moment it's used — a repeat attempt gets a brand-new one, not a replay of the old. A blocked attempt (session limit reached) does not consume it, so the confirmed retry reuses the same code.

/verify-token

Validate an access_token on protected requests. Returns the user's identity and permissions.

POST/api/v1/verify-token
Request
{ "access_token": "eyJhbGciOi…" }

/refresh-token

Mints a new access_token from the refresh_token. The session itself doesn't expire on a schedule — it's valid until logout, deactivation, or deletion.

POST/api/v1/refresh-token
Request
{ "refresh_token": "eyJhbGciOi…" }

This is the most common integration bug. The access token only lives ~15 minutes. If your backend doesn't catch a 401 and call this endpoint, users get logged out constantly — "session stays valid until logout" is a promise your code has to keep, not something the tokens do on their own. See Keeping users signed in.

/logout

Ends the session and revokes the trusted device for that (user, app) pair. The next login there needs a fresh OTP again — this isn't just "end this session," it's "forget this device."

POST/api/v1/logout
Request
{ "refresh_token": "eyJhbGciOi…" }

/app-users

Every user registered (granted access) to your application — identified purely by the X-Client-Id/X-Client-Secret headers, no app_id parameter, so you can only ever list your own users, never another app's.

GET/api/v1/app-users
Success
{
  "status": "success",
  "users": [
    {
      "user_id": "6a858c8b52122ad2afac2905",
      "name": "Jane Doe",
      "email": "jane@example.com",
      "department": "Engineering",
      "status": "active",
      "is_test_user": false,
      "test_access_expires_at": null,
      "role": "App Admin",
      "permissions": ["*"],
      "granted_at": "2026-08-19T11:18:21.611Z"
    }
  ]
}

Each entry includes the user's department and the role/permissions for this app specifically — the same person can hold a different role on a different app.

OTP is per device, not per login

Passwords never expire. Password alone never completes a login on a device that hasn't proven itself yet.

SituationWhat happens
New device, first attemptotp_required — superadmin shares a fresh code
Same device, future loginsSends stored device_token → skips OTP entirely
Different device / cleared storageAlways challenged fresh, regardless of past history
User calls logoutTrusted device revoked too — next login there needs a fresh OTP
Superadmin revokes manuallySame effect, without waiting for the user to log out

Concurrent-login limit

Each application has a max_active_sessions setting (default 1, set by the superadmin per app). Hitting it doesn't silently sign the older session out.

RESPONSEfrom verify-login or verify-otp
{
  "status": "session_limit_reached",
  "message": "you're already logged in elsewhere…",
  "max_active_sessions": 1,
  "active_sessions": [
    { "session_id": "…", "ip_address": "203.0.113.4", "user_agent": "Mozilla/5.0 …", "created_at": "2026-09-05T10:00:00Z" }
  ]
}

This is checked as early as possible — on a brand-new device, verify-login checks it right after the password is validated, before an OTP is even generated or emailed.

1
Detect status === "session_limit_reached" instead of treating it as a plain error.
2
Show the user active_sessions — at minimum the IP/user-agent and when it started, ideally with a checkbox per session.
3
If they confirm, resend the exact same request with force_logout_others: true (kill everything) or logout_session_ids: [...] (kill only what's selected — for a limit above 1) added.
4
On the trusted-device path or verify-otp, that completes the login (status: "success"). On a brand-new device's verify-login, it instead goes back to otp_required — the conflict is cleared, but that device still has to prove itself with a code.

A blocked verify-otp attempt doesn't consume the OTP — the confirmed retry reuses the same code, no new one needed. Selecting too few session ids to clear the limit returns session_limit_reached again with whatever's left, not an error.

Test users

A user can be marked as a test user with an access-end date — the superadmin picks a day, and access runs through the end of that day (UTC).

{ "status": "error", "message": "test access has expired, contact your superadmin" }

An access token issued before expiry keeps working until its own ~15-minute lifetime ends — the next refresh-token call after that is what actually tears the session down, same latency as deactivation.

Keeping users signed in

"Session stays valid until logout" only happens if your backend implements the refresh call — the tokens alone don't do it.

1
Store access_token, refresh_token, and device_token from verify-otp — a common bug is only keeping the access token, which makes sessions expire in 15 minutes no matter what.
2
Catch a 401 on any protected request → POST /refresh-token with the refresh_token.
3
On {status:"success"}, retry the original request once with the new access_token.
4
On {status:"error"}, the refresh_token itself is gone (logout/deactivated/deleted) — this is the one case where you send the user to a real login.

If you use cookies + server-side route protection (Next.js middleware.ts, an Express guard — anything that runs before a protected page renders), that guard needs the same refresh logic, separately from your API client's retry. A guard that only checks "is the access-token cookie present?" bounces users to a full login screen every ~15 minutes, even though refresh_token is still valid for years. Missing access token ≠ logged out — only a failed refresh is a real logout.
