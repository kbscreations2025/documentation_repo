1. Authenticate every request

Every call to /api/v1/* is made server-to-server from your application's own backend and must carry these two headers. The response envelope is always { status: "success" | "otp_required" | "error", ... }, identical across every endpoint below. 


  


  

    
OTP is per-device, not per-login

    

      Passwords never expire, and password alone never completes a login on a device that hasn't
      proven itself yet. verify-login returns otp_required the first time
      a device logs in — the superadmin reveals a fresh 6-digit code (valid 15 minutes) from the
      Users tab and shares it with the user out-of-band, and your app calls verify-otp
      to get tokens and a device_token.
    

    

      Store that device_token (alongside the access/refresh tokens) and send it back
      on every future verify-login from that same device — the OTP step is skipped
      entirely and tokens come back directly. A different device (browser, phone, cleared storage
      — anywhere that doesn't have this exact token) always gets challenged fresh. Calling
      logout revokes that device's trust too, not just the session — it's "forget this
      device," so the next login (even the same device) needs a fresh OTP again.
    

  


  

    
Concurrent-login limit (default 1 per app)

    

      Every application has a max_active_sessions setting, configurable per app from
      the Applications tab, default 1. If a user already has that many active
      sessions on an app and completes another login, the API does not silently sign out
      the older session — it returns { status: "session_limit_reached" } with the
      existing session(s)' IP address, browser, and login time. On a brand-new device this is
      checked right after the password is validated, before an OTP is generated or
      emailed, so a blocked device finds out immediately.
    

    

      Your screen for this needs to: (1) detect this shape instead of treating it as a plain
      error, (2) show the existing session(s), ideally with a checkbox per session, (3) resend the
      exact same request with either force_logout_others: true (kills every
      blocking session) or logout_session_ids: [...] (kills only the ones selected —
      for a limit above 1) to proceed, and (4) if the user cancels, just discard the response —
      nothing changed server-side.
    

    

      A blocked verify-otp attempt does not consume the OTP, so a confirmed retry
      reuses the same code.
    

  


  

    
Test users (time-boxed access)

    

      A user can be marked as a test user with an access-end date (a day, not an exact time —
      access runs through the end of that day UTC). Past that date, verify-login and
      verify-otp return
      { status: "error", message: "test access has expired, contact your superadmin" }
      instead of tokens.
    

    

      An access token issued before expiry keeps working until its own ~15-minute
      lifetime ends — the next refresh-token call after that is what actually tears
      the session down.
    

  


  

    
Keeping users signed in (read this before you ship)

    

      "Session stays valid until logout" only happens if your backend actually implements
      the refresh call. The access token expires in 15 minutes; every protected request your
      backend makes needs to catch a 401, exchange the refresh_token for a new
      access_token, and retry once. Skipping this is the single most common
      integration bug.
    

    
async function callWithAutoRefresh(accessToken, refreshToken, doRequest) {
  try {
    return await doRequest(accessToken);
  } catch (err) {
    if (err.status !== 401) throw err;

    const refreshed = await fetch("/api/v1/refresh-token", {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        "X-Client-Id": "",
        "X-Client-Secret": "<client_secret>",
      },
      body: JSON.stringify({ refresh_token: refreshToken }),
    }).then((r) => r.json());

    if (refreshed.status !== "success") {
      throw new Error("session ended, please log in again");
    }

    return await doRequest(refreshed.access_token);
  }
}

    

      Store access_token, refresh_token, and
      device_token from verify-otp — only keeping the access token is
      what makes sessions expire in 15 minutes no matter what.
    

  


  

    
If you use cookies + server-side route protection, refresh there too

    

      A guard that only checks "is the access-token cookie present?" will bounce users to a full
      login screen every time the access token's normal short lifetime runs out, even though the
      refresh_token (valid for years) is still perfectly good. Missing access token
      ≠ logged out; only a failed refresh is a real logout.
    

    
async function guardRoute(request) {
  let accessToken = request.cookies.get("access_token");

  if (!accessToken) {
    const refreshToken = request.cookies.get("refresh_token");
    if (refreshToken) {
      const refreshed = await callYourOwnRefreshEndpoint(refreshToken);
      if (refreshed.status === "success") {
        accessToken = refreshed.access_token;
      }
    }
  }

  if (!accessToken) return redirectToLogin();
  return allowRequestThrough(accessToken);
}

    

      Pure client-side SPAs storing tokens in localStorage (no server-side route
      guard) don't have this problem.
